   161→## 2. Legacy Sales Workflow — End-to-End Pipeline
   162→
   163→### 2.1 Sales Invoice Lifecycle State Machine
   164→
   165→```
   166→┌───────────────────────────────────────────────────────────────┐
   167→│                    SALES PIPELINE (4 Stages)                   │
   168→│                                                               │
   169→│  ① DRAFT INVOICE                                              │
   170→│  │  Controller: SalesController::final_sales()                │
   171→│  │  Service:   SalesInvoiceService::finalizeSales()           │
   172→│  │  GL:        Dr AR / Cr Revenue                             │
   173→│  │  Ledger:    customer_ledger DEBIT (running_balance += amt) │
   174→│  │  Stock:     Soft hold via sales_invoice_dispatches          │
   175→│  │             (ordered_qty set, dispatched_qty = 0)          │
   176→│  │                                                             │
   177→│  ↓  (can delete draft, can edit draft)                        │
   178→│                                                               │
   179→│  ② GODOWN ISSUED                                              │
   180→│  │  Controller: ChallanController::prepare_godown()           │
   181→│  │  Service:   ChallanModel::prepareGodown()                  │
   182→│  │  GL:        NONE (warehouse assignment only)               │
   183→│  │  Stock:     NO physical movement yet                       │
   184→│  │  Effect:    warehouse_id assigned to items + dispatches    │
   185→│  │             status → godown_issued                          │
   186→│  │             dispatchers assigned                            │
   187→│  │             transport_cost captured                         │
   188→│  │                                                             │
   189→│  ↓  (can reverse godown → back to draft)                      │
   190→│                                                               │
   191→│  ③ CHALLAN COMPLETED                                          │
   192→│  │  Controller: ChallanController::create_final_challan()     │
   193→│  │  Service:   ChallanModel::finalizeChallan()                │
   194→│  │  GL:        Dr COGS / Cr Inventory (at avg_cost)           │
   195→│  │  Ledger:    customer_ledger ADJUSTMENT (if transport delta)│
   196→│  │  Stock:     Physical OUT from warehouse_stock               │
   197→│  │             dispatched_qty = ordered_qty                    │
   198→│  │  Snapshot:  pre_challan_transport/total saved               │
   199→│  │             sales_challan_items (issue_rate, cogs_amount)   │
   200→│  │                                                             │
   201→│  ↓  (can reverse challan → back to godown_issued)             │
   202→│                                                               │
   203→│  ④ PAYMENT RECEIVED                                           │
   204→│     Controller: SalesController::save_payment()               │
   205→│                OR CustomerTransactionController::store()      │
   206→│     Service:   SalesPaymentService::recordCustomerPayment()   │
   207→│                OR CustomerTransactionModel::createTransaction()│
   208→│     GL:        Dr Cash/Bank / Cr AR                           │
   209→│     Ledger:    customer_ledger CREDIT (running_balance -= amt)│
   210→│     Settlement: invoice_payment_allocations                    │
   211→│     Interco:   BranchIntercompanyService (bank-mode only)     │
   212→└───────────────────────────────────────────────────────────────┘
   213→```

   215→### 2.2 Sales Return Two-Phase Flow
   216→
   217→```
   218→┌───────────────────────────────────────────────────────────────┐
   219→│                  SALES RETURN PIPELINE (2 Phases)              │
   220→│                                                               │
   221→│  ① PHASE 1 — CREATE RETURN (Sales Manager)                    │
   222→│  │  Controller: SalesReturnController::store()                │
   223→│  │  Service:   SalesReturnModel::createReturn()               │
   224→│  │  GL:        NONE (draft return)                             │
   225→│  │  Stock:     NO movement yet                                 │
   226→│  │  Validates: invoice status = challan_completed              │
   227→│  │             returnable_qty = invoice_qty - already_returned │
   228→│  │                                                             │
   229→│  ↓                                                             │
   230→│                                                               │
   231→│  ② PHASE 2 — WAREHOUSE CONFIRM                                │
   232→│     Controller: SalesReturnController::confirm_store()        │
   233→│     Service:   SalesReturnModel::confirmReturn()              │
   234→│                                                               │
   235→│     For GOOD condition items:                                  │
   236→│     ├── Stock IN at ORIGINAL avg_cost (not current)            │
   237→│     ├── GL Revenue Reversal: Dr Sales Return / Cr AR          │
   238→│     ├── GL COGS Reversal: Dr Inventory / Cr COGS              │
   239→│     └── Customer ledger CREDIT (customer owes less)           │
   240→│                                                               │
   241→│     For DAMAGE condition items:                                │
   242→│     ├── Stock IN at ORIGINAL avg_cost (temporarily)            │
   243→│     ├── Auto-create damage_invoices via DamageService          │
   244→│     ├── Stock OUT immediately (write-off)                      │
   245→│     ├── GL: Dr Shrinkage / Cr Inventory                       │
   246→│     ├── Link: sales_return_items.damage_invoice_id             │
   247→│     └── Customer still gets credit for the return              │
   248→│                                                               │
   249→│  (can reverse return → undoes all stock + GL + damage)        │
   250→└───────────────────────────────────────────────────────────────┘
   251→```

   253→### 2.3 GL Posting Points Summary
   254→
   255→| Action | Debit | Credit | Trigger Point |
   256→|--------|-------|--------|---------------|
   257→| Invoice finalize | AR | Revenue (+ Discount contra, Transport revenue) | `final_sales()` |
   258→| Godown prep | — | — | `prepare_godown()` (NO GL) |
   259→| Challan finalize | COGS | Inventory | `create_final_challan()` |
   260→| Transport adjustment (increase) | AR | Transport Revenue | `create_final_challan()` (if delta) |
   261→| Transport adjustment (decrease) | Transport Revenue | AR (reversal) | `create_final_challan()` (if delta) |
   262→| Payment received (cash) | Cash | AR | `save_payment()` / `store()` |
   263→| Payment received (bank) | Bank | AR | `save_payment()` / `store()` |
   264→| Return confirmed (Good) — Revenue reversal | Sales Return | AR | `confirmReturn()` |
   265→| Return confirmed (Good) — COGS reversal | Inventory | COGS | `confirmReturn()` |
   266→| Return confirmed (Damage) — Write-off | Shrinkage | Inventory | `confirmReturn()` → auto damage |
   267→| Manual damage | Shrinkage | Inventory | DamageService |

   269→### 2.4 Stock Movement Rules
   270→
   271→| Event | Direction | Rate | Effect on avg_cost |
   272→|-------|-----------|------|--------------------|
   273→| Purchase receive | IN | Purchase rate | **Recalculated** (weighted average) |
   274→| Challan finalize (stock OUT) | OUT | Current avg_cost | **Unchanged** (standard accounting) |
   275→| Sales return confirm (Good) | IN | ORIGINAL avg_cost from challan | **Recalculated** (weighted average with original cost) |
   276→| Sales return confirm (Damage) | IN then OUT | Original then avg_cost | IN recalculates, OUT unchanged |
   277→| Damage write-off | OUT | Current avg_cost | **Unchanged** |
   278→| Warehouse transfer (source) | OUT | Current avg_cost | **Unchanged** |
   279→| Warehouse transfer (dest) | IN | Source avg_cost | **Recalculated** |
   280→| Branch demand fulfillment (source) | OUT | Current avg_cost | **Unchanged** |
   281→| Branch demand fulfillment (dest) | IN | Source avg_cost | **Recalculated** |
   282→
   283→**Moving Average Formula (Stock IN):**
   284→```
   285→new_avg_cost = (old_qty × old_avg + in_qty × in_rate) / (old_qty + in_qty)
   286→```
   287→
   288→**Stock Availability Formula (SSOT):**
   289→```
   290→available_qty = GREATEST(0, physical_qty - pipeline_qty)
   291→pipeline_qty = SUM(ordered_qty - dispatched_qty)
   292→  FROM sales_invoice_dispatches
   293→  JOIN sales_invoices ON ...
   294→  WHERE NOT reversed, NOT challan_completed/cancelled
   295→  AND ordered_qty > dispatched_qty
   296→```

   300→## 3. Legacy Business Logic — Deep Documentation
   301→
   302→### 3.1 Invoice Finalization (finalizeSales) — 9-Step Atomic
   303→
   304→1. **Validate customer + cart not empty** — must have customer_id and at least one item
   305→2. **Calculate totals** — `subtotal = Σ(qty × rate)`, `total_amount = subtotal + transport_cost - discount_amount`
   306→3. **Credit limit enforcement** — `wouldExceedCreditLimit(customerId, newAmount)`:
   307→   - `currentDue = latest customer_ledger.running_balance`
   308→   - If `credit_limit > 0` AND `currentDue + newAmount > credit_limit + 0.01`:
   309→     - Without override → return `{status: 'credit_limit_exceeded'}`
   310→     - With override → require `override_reason` ≥ 10 characters
   311→4. **Pre-transaction stock + rate validation** — `StockAvailabilityService::assertBranchProductsAvailable()` + `validateRateInRange()`
   312→5. **DB TRANSACTION begins**:
   313→   - a. Lock branch products `SELECT warehouse_stock FOR UPDATE`
   314→   - b. Re-verify stock inside lock (race condition protection)
   315→   - c. Generate invoice code (e.g., `SI-20250120-001`) via `document_sequences SELECT FOR UPDATE`
   316→   - d. INSERT `sales_invoices` (status='draft')
   317→   - e. INSERT `sales_invoice_items` (warehouse_id=NULL at this stage)
   318→   - f. INSERT `sales_invoice_dispatches` (ordered_qty, dispatched_qty=0) — **soft reservation**
   319→   - g. INSERT `customer_ledger` DEBIT (running_balance = previous + total_amount)
   320→   - h. Post GL via `JournalPostingService::postSalesInvoice()` — Dr AR / Cr Revenue
   321→   - i. Link `journal_entry_id` on `sales_invoices`
   322→6. **COMMIT** → clear session cart
   323→7. **On error** → ROLLBACK
   324→
   325→### 3.2 Invoice Update (updateExistingInvoice) — 10-Step Atomic
   326→
   327→1. Load old invoice, verify **editability guards**: draft, no godown, no payments, not reversed
   328→2. Load cart items, calculate new totals
   329→3. **Credit limit check on NET INCREASE only** — `max(0, newTotal - oldTotal)` (key improvement over full-amount check)
   330→4. **DB TRANSACTION begins**:
   331→   - a. Re-lock invoice `FOR UPDATE`
   332→   - b. Lock branch products `FOR UPDATE`
   333→   - c. Re-verify stock (exclude current invoice's dispatches)
   334→   - d. Reverse old customer_ledger (credit the old debit)
   335→   - e. New customer_ledger debit
   336→   - f. UPDATE `sales_invoices`
   337→   - g. DELETE old items + dispatches + dispatchers → re-insert new ones
   338→   - h. Reverse prior GL journal → post new journal
   339→   - i. Reset `is_godown_prepared = false` (edit invalidates godown assignment)
   340→5. **COMMIT**
   341→
   342→### 3.3 Godown Preparation (prepareGodown) — 5-Step Atomic
   343→
   344→1. **DB TRANSACTION begins**:
   345→   - a. Lock invoice `SELECT ... FOR UPDATE` — verify status='draft' (legacy) or 'confirmed' (Laravel), not reversed
   346→   - b. Validate each warehouse assignment has sufficient physical stock
   347→   - c. UPDATE `sales_invoice_items` SET `warehouse_id` for each line
   348→   - d. DELETE + re-INSERT `sales_invoice_dispatches` (with warehouse_id)
   349→   - e. INSERT `sales_invoice_dispatchers` (if dispatchers selected)
   350→   - f. UPDATE `sales_invoices` SET `status = 'godown_issued'` (legacy) / `is_godown_prepared = true` (Laravel), `godown_issued_at = NOW()`
   351→   - g. Capture `transport_cost` (may differ from initial invoice transport)
   352→2. **COMMIT**
   353→3. **NO GL posting** — no financial effect at this stage
   354→4. **NO stock movement** — physical stock unchanged
   355→
   356→### 3.4 Challan Finalization (finalizeChallan) — 8-Step Atomic
   357→
   358→1. Assert godown is prepared, not already challan-issued
   359→2. **DB TRANSACTION begins**:
   360→   - a. Lock invoice + challan `FOR UPDATE`
   361→   - b. Generate challan code via `document_sequences SELECT FOR UPDATE`
   362→   - c. For each item:
   363→      - Get current `avg_cost` from `warehouse_stock`
   364→      - **Stock OUT**: negative qty via `StockTransactionModel::updateWarehouseStock()`
   365→      - Snapshot per-line cost into `sales_challan_items` (issue_rate, cogs_amount)
   366→      - UPDATE `sales_invoice_dispatches` SET `dispatched_qty = ordered_qty`
   367→      - Accumulate `cogsTotal += qty × avg_cost`
   368→   - d. INSERT `sales_challans` header
   369→   - e. **Transport adjustment** (if challan transport ≠ invoice transport):
   370→      - Snapshot original: `pre_challan_transport`, `pre_challan_total`
   371→      - Post `customer_ledger` ADJUSTMENT entry (running_balance delta)
   372→      - Post GL adjustment: Dr AR / Cr Transport Revenue (positive delta) or reverse (negative delta)
   373→   - f. Post GL: **Dr COGS / Cr Inventory** (single journal for all lines)
   374→   - g. Link `journal_entry_id` + `cogs_journal_entry_id` on `sales_invoices`
   375→   - h. UPDATE `sales_invoices` SET `is_challan_issued = true`, `challan_issued_at = NOW()`
   376→3. **COMMIT**
   377→4. Send Telegram notification
   378→
   379→**Key insight**: Revenue is recognized at **invoice finalize** (accrual basis), but COGS is recognized at **challan finalize** (when goods physically leave warehouse). This creates a timing gap that gross margin reports must account for.
   380→
   381→### 3.5 Payment Recording (recordCustomerPayment) — 7-Step Atomic
   382→
   383→1. Parse payment_mode (cash/bank) and bank_id
   384→2. **DB TRANSACTION begins**:
   385→   - a. If invoice_id: lock invoice `FOR UPDATE`, verify not reversed, branch accessible
   386→   - b. Check payment doesn't exceed invoice balance: `paidSoFar + amount <= total_amount + 0.01`
   387→   - c. Generate payment_code via `document_sequences`
   388→   - d. INSERT `customer_payments`
   389→   - e. INSERT `customer_ledger` CREDIT (running_balance -= amount)
   390→   - f. If invoice_id: INSERT `invoice_payment_allocations`
   391→   - g. Post GL: **Dr Bank/Cash / Cr AR**
   392→   - h. Link `journal_entry_id` on `customer_payments`
   393→   - i. Inter-branch settlement (bank-mode only): `BranchIntercompanyService::settleFromCustomerPayment()`
   394→3. **COMMIT**
   395→4. Return payment_id, payment_code, balance_due, is_fully_paid
   396→
   397→### 3.6 Payment Reversal (reverseCustomerPayment) — 8-Step Atomic
   398→
   399→1. **DB TRANSACTION begins**:
   400→   - a. Lock payment `FOR UPDATE`, verify not reversed, transaction_type='receive'
   401→   - b. Load allocations + verify branch access
   402→   - c. Reverse linked GL journal (append-only reversing entry)
   403→   - d. Reverse inter-branch settlements
   404→   - e. INSERT `customer_ledger` DEBIT reversal (running_balance += amount)
   405→   - f. DELETE `invoice_payment_allocations`
   406→   - g. Soft-delete payment: `is_reversed = 1`, `reversed_at`, `reversed_by`, `reverse_reason`
   407→2. **COMMIT**
   408→
   409→### 3.7 Sales Return Creation (createReturn) — Phase 1
   410→
   411→1. Validates invoice is `challan_completed` (not draft, not already returned fully)
   412→2. **returnable_qty** per item = `invoiceItem.qty - SUM(already returned qty from non-reversed/non-cancelled returns)`
   413→3. Creates `sales_returns` with status='pending' (legacy) / 'created' (Laravel)
   414→4. Snapshots `original_cost` from challan's `stock_transactions` — **NOT current avg_cost**
   415→5. **NO GL, NO stock movement** at this stage
   416→6. Sends Telegram notification to admins
   417→
   418→### 3.8 Sales Return Confirmation (confirmReturn) — Phase 2, Multi-Step Atomic
   419→
   420→1. **DB TRANSACTION begins**:
   421→   - a. Lock return + items `FOR UPDATE`, verify status='pending'/'created'
   422→   - b. For each Good condition item:
   423→      - Stock IN at `original_cost` (avg_cost recalculated by weighted average rule)
   424→      - GL Revenue Reversal: **Dr Sales Return / Cr AR** (at sales rate)
   425→      - GL COGS Reversal: **Dr Inventory / Cr COGS** (at original avg_cost)
   426→   - c. For each Damage condition item:
   427→      - Stock IN at `original_cost` (temporarily)
   428→      - Auto-create `damage_invoices` via DamageService:
   429→        - Draft damage → immediately confirm → Stock OUT at avg_cost
   430→        - GL: **Dr Shrinkage / Cr Inventory**
   431→      - Link `sales_return_items.damage_invoice_id → damage_invoices.id`
   432→   - d. INSERT `customer_ledger` CREDIT (running_balance -= total_return_amount)
   433→   - e. Link `journal_entry_id` + `cogs_journal_entry_id` on `sales_returns`
   434→2. **COMMIT**
   435→3. Sends Telegram notification
   436→
   437→### 3.9 Sales Return Reversal (reverseReturn) — Multi-Step Atomic
   438→
   439→1. Pre-check: `can_reverse` flag, sufficient on-hand stock to remove returned items
   440→2. **DB TRANSACTION begins**:
   441→   - a. Lock return `FOR UPDATE`
   442→   - b. **Reverse linked damage write-offs FIRST** (order matters!)
   443→   - c. Reverse each stock movement from the return (Stock OUT for Good items that were returned to warehouse)
   444→   - d. Reverse both GL journals (revenue + COGS)
   445→   - e. Reverse customer_ledger (debit entry, running_balance += amount)
   446→3. **COMMIT**
   447→
   448→### 3.10 Credit Limit Enforcement
   449→
   450→```
   451→Formula:
   452→  currentDue = latest customer_ledger.running_balance (for customer)
   453→  projectedDue = currentDue + newInvoiceAmount
   454→  exceeds = (credit_limit > 0) AND (projectedDue > credit_limit + 0.01)
   455→  
   456→  If exceeds AND no override → BLOCK with credit_limit_exceeded
   457→  If exceeds AND override + reason ≥ 10 chars → ALLOW with audit log
   458→```
   459→
   460→**Edge cases:**
   461→- `credit_limit = 0` → no enforcement (unlimited credit)
   462→- Override is tracked: `sale_credit_limit_override` audit event
   463→- Invoice update only checks net increase: `max(0, newTotal - oldTotal)`
   464→
   465→### 3.11 Stale Draft Cleanup
   466→
   467→- **Threshold**: Configurable (default 14 days)
   468→- **Criteria**: `status='draft'`, `is_godown_prepared=false`, `is_challan_issued=false`, `is_reversed=false`
   469→- **Batch limit**: 200 per run
   470→- **Dry-run mode**: Supported
   471→- **Scheduled**: Daily at 02:00 (configurable on/off)
   472→- **Audit**: Each cancellation logged to `user_audit_log`
   473→
   474→### 3.12 Customer Ledger Running Balance
   475→
   476→```
   477→Each financial event posts a row to customer_ledger:
   478→  invoice      → DEBIT  (customer owes more): balance = prev + amount
   479→  payment      → CREDIT (customer owes less): balance = prev - amount
   480→  return       → CREDIT (customer owes less): balance = prev - amount
   481→  reversal     → Opposite of original (compensating entry)
   482→  invoice_adj  → DELTA  (transport change at challan): balance = prev ± delta
   483→  
   484→SSOT for customer due: latest running_balance row for the customer
   485→```
   486→
   487→### 3.13 Branch Isolation
   488→
   489→All sales operations enforce `sessionBranchId()`:
   490→- `assertInvoiceAccessible()` — throws if invoice belongs to different branch
   491→- `warehouseBelongsToBranch()` — validates warehouse ownership
   492→- Admin/manager can override with `canOverrideBranch()`
   493→- Override is logged: `branch_override` audit event
   494→
   495→### 3.14 Inter-Branch Settlement (Bank Payments)
   496→
   497→When a bank payment is received at Branch A for a customer who owes Branch B:
   498→1. Payment GL posts normally (Dr Bank / Cr AR) at Branch A
   499→2. `BranchIntercompanyService::settleFromCustomerPayment()` fires:
   500→   - Iterates all creditor branches (branches the customer owes)
   501→   - FIFO settles inter-branch demands: oldest first
   502→   - Creates `branch_ledger` entries (debtor Dr / creditor Cr)
   503→   - Posts intercompany GL: Dr Interbranch Payable / Cr Interbranch Receivable
   504→3. Cash payments do NOT trigger intercompany settlement (use money transfers instead)

   535→### 4.2 Key Schema Differences (MySQL → PostgreSQL)
   536→
   537→#### Status Values Migration
   538→
   539→| Table | MySQL ENUM | PG CHECK | ETL Conversion |
   540→|-------|-----------|----------|---------------|
   541→| `sales_invoices.status` | draft, godown_issued, challan_completed, cancelled, reversed | draft, confirmed, cancelled, reversed | `godown_issued` → `confirmed` + `is_godown_prepared=true`; `challan_completed` → `confirmed` + both flags true |
   542→| `sales_returns.status` | pending, completed, reversed | created, confirmed, reversed | `pending` → `created`; `completed` → `confirmed` |
   543→
   544→**Key design change**: Legacy used ENUM status progression (draft → godown_issued → challan_completed). Laravel uses **boolean flags** (`is_godown_prepared`, `is_challan_issued`) alongside a simpler status CHECK. This is more flexible and avoids ALTER TYPE for new statuses.
   545→
   546→#### MySQL Features Converted to PostgreSQL
   547→
   548→| MySQL Feature | PostgreSQL Equivalent | Concern |
   549→|--------------|----------------------|---------|
   550→| `ENUM` types | `VARCHAR + CHECK IN (...)` | ⚠️ Adding new values requires ALTER CHECK constraint |
   551→| `AUTO_INCREMENT` | `GENERATED ALWAYS AS IDENTITY` | ✅ Superior — no gaps from rollbacks |
   552→| `ON UPDATE CURRENT_TIMESTAMP` | Trigger `update_updated_at_column()` + BEFORE UPDATE trigger per table | ⚠️ Must ensure all tables have trigger |
   553→| `float(20,2)` for money | `numeric(18,2)` | 🔴 CRITICAL — Float has precision loss |
   554→| `int(11) storing YYYYMMDD` | `date` with `CURRENT_DATE` | 🔴 CRITICAL — ETL conversion needed |
   555→| `0000-00-00 00:00:00` dates | `NULL` | ⚠️ pgloader zero-dates-to-null |
   556→| `ON DUPLICATE KEY UPDATE` | `INSERT ... ON CONFLICT DO UPDATE` | ✅ Native equivalent |
   557→| `IF()` in GENERATED columns | `CASE WHEN ... THEN ... ELSE ... END` | ✅ Clean |
   558→| `SIGNAL SQLSTATE '45000'` | `RAISE EXCEPTION USING ERRCODE = 'check_violation'` | ✅ Clean |
   559→| Backtick identifiers | Removed (unquoted, PG folds to lowercase) | ✅ Clean |
   560→| `DATE_FORMAT / CURDATE / DATEDIFF` | `to_char() / CURRENT_DATE / (a::date - b::date)` | ✅ Clean |

   779→| ✅ | **Atomic document code generation** | `document_sequences` with `SELECT FOR UPDATE` replaces legacy `COUNT+1` race condition. |

   783→| ✅ | **Per-line COGS snapshot** | `sales_challan_items.issue_rate` captures exact avg_cost at time of OUT. |
   784→| ✅ | **Original cost lookup for returns** | Ensures COGS reversal matches exactly; avg_cost restored correctly. |
   785→| ✅ | **Linked damage write-offs** | Properly chains damage invoices to sales returns with correct reversal ordering. |
   786→| ✅ | **GENERATED STORED columns** | `sales_invoice_items.amount`, `sales_return_items.amount` — eliminates PHP calculation drift. |

   796→## 7. PostgreSQL Power Features — Optimization Plan
   797→
   798→The user specifically requested to **"use the total power of PostgreSQL so we don't have to fall in any issue in long term."** Below is a comprehensive plan for PostgreSQL-specific optimizations that go beyond what's currently implemented.
   799→
   800→### 7.1 GENERATED Columns — Expand Usage
   801→
   802→Currently only `amount` on `sales_invoice_items` and `sales_return_items` is GENERATED. Additional candidates:
   803→
   804→| Table | Column | Expression | Benefit |
   805→|-------|--------|-----------|---------|
   806→| `sales_invoices` | `due_amount` | `GREATEST(0, total_amount - paid_amount)` | Always in sync, never stale |
   807→| `sales_challans` | `issue_cost` | `(SELECT SUM(cogs_amount) FROM sales_challan_items WHERE sales_challan_id = sales_challans.id)` | Eliminates denormalization drift |
   808→| `sales_returns` | `cogs_amount` | `(SELECT SUM(qty * original_cost) FROM sales_return_items WHERE sales_return_id = sales_returns.id)` | Auto-computed, no service maintenance |
   809→| `warehouse_stock` | `stock_value` | `qty * avg_cost` | Always-current inventory valuation |
   810→
   811→**Why this matters for long-term**: GENERATED columns are **always correct** — no service can forget to update them, no bug can make them stale. This eliminates an entire class of data inconsistency bugs.
   812→
   813→### 7.2 Partial Indexes — Expand for Query Patterns
   814→
   815→Currently 5 partial indexes exist. Additional high-value candidates:
   816→
   817→```sql
   818→-- Open invoices (most queried subset)
   819→CREATE INDEX idx_si_open ON sales_invoices (branch_id, invoice_date)
   820→  WHERE status IN ('draft', 'confirmed') AND is_reversed = false;
   821→
   822→-- Unpaid invoices (AR aging, collection priority)
   823→CREATE INDEX idx_si_unpaid ON sales_invoices (customer_id, due_amount)
   824→  WHERE due_amount > 0 AND is_reversed = false;
   825→
   826→-- Pending returns (warehouse action needed)
   827→CREATE INDEX idx_sr_pending ON sales_returns (branch_id, return_date)
   828→  WHERE status = 'created' AND is_reversed = false;
   829→
   830→-- Non-reversed customer ledger (99% of queries)
   831→CREATE INDEX idx_cl_active ON customer_ledger (customer_id, transaction_date)
   832→  WHERE is_reversed = false;
   833→
   834→-- Bank-mode payments (intercompany settlement queries)
   835→CREATE INDEX idx_cp_bank ON customer_payments (bank_id, payment_date)
   836→  WHERE payment_mode = 'bank' AND is_reversed = false;
   837→```
   838→
   839→**Why this matters for long-term**: Partial indexes are **smaller** (only relevant rows) and **faster** (fewer pages to scan). As data grows, the gap between full and partial indexes widens dramatically.
   840→
   841→### 7.3 Covering Indexes (INCLUDE) — Avoid Heap Lookups
   842→
   843→```sql
   844→-- Today's invoices DataTable: needs code, date, customer, total, status, paid, due
   845→CREATE INDEX idx_si_today ON sales_invoices (branch_id, invoice_date)
   846→  INCLUDE (invoice_code, customer_id, total_amount, status, paid_amount, due_amount, is_godown_prepared, is_challan_issued);
   847→
   848→-- Customer balance lookup: needs latest running_balance
   849→CREATE INDEX idx_cl_balance ON customer_ledger (customer_id, id DESC)
   850→  INCLUDE (balance, is_reversed);
   851→
   852→-- Stock availability: needs qty + avg_cost
   853→CREATE INDEX idx_ws_stock ON warehouse_stock (warehouse_id, product_id)
   854→  INCLUDE (qty, avg_cost);
   855→```
   856→
   857→**Why this matters for long-term**: Covering indexes enable **index-only scans** — PostgreSQL never needs to visit the heap (actual table pages). For frequently queried columns, this can be 5-10x faster on large tables.
   858→
   859→### 7.4 BRIN Indexes — For Time-Series Data
   860→
   861→```sql
   862→-- sales_invoices inserted chronologically → BRIN is ideal
   863→CREATE INDEX idx_si_created_brin ON sales_invoices USING BRIN (created_at)
   864→  WITH (pages_per_range = 32);
   865→
   866→-- stock_transactions appended chronologically
   867→CREATE INDEX idx_st_date_brin ON stock_transactions USING BRIN (transaction_date)
   868→  WITH (pages_per_range = 32);
   869→
   870→-- customer_ledger appended chronologically
   871→CREATE INDEX idx_cl_date_brin ON customer_ledger USING BRIN (created_at)
   872→  WITH (pages_per_range = 32);
   873→```
   874→
   875→**Why this matters for long-term**: BRIN indexes are **tiny** (~0.1% of table size vs ~10% for B-tree) and perfect for append-only time-series data. They're essentially free to maintain and dramatically speed up date-range queries on large tables.
   876→
   877→### 7.5 JSONB Indexing — Cart + Configuration Queries
   878→
   879→```sql
   880→-- GIN index for JSONB cart items (product lookups within cart)
   881→CREATE INDEX idx_sdc_items ON sales_draft_carts USING GIN (items_json jsonb_path_ops);
   882→
   883→-- Example query this enables:
   884→-- SELECT * FROM sales_draft_carts WHERE items_json @> '[{"product_id": 42}]';
   885→```
   886→
   887→**Why this matters for long-term**: As cart complexity grows (multi-warehouse, condition tracking), GIN indexes enable fast lookups within JSON structures without full table scans.
   888→
   889→### 7.6 Advisory Locks — Replace SELECT FOR UPDATE for Code Generation
   890→
   891→Currently `document_sequences` uses `SELECT FOR UPDATE` for atomic code generation. PostgreSQL advisory locks are faster:
   892→
   893→```sql
   894→-- Instead of: SELECT counter FROM document_sequences WHERE ... FOR UPDATE
   895→-- Use: pg_advisory_xact_lock(hash) → then SELECT/UPDATE without FOR UPDATE
   896→
   897→-- Laravel:
   898→DB::select("SELECT pg_advisory_xact_lock(?, ?)", [$branchId, $typeHash]);
   899→$next = DB::selectOne("SELECT nextval('doc_seq_$type')");
   900→```
   901→
   902→**Why this matters for long-term**: Advisory locks are **in-memory** (no disk I/O), **transaction-scoped** (auto-released on commit/rollback), and **don't block reads**. Under high concurrency, they outperform row-level locks significantly.
   903→
   904→### 7.7 LISTEN/NOTIFY — Replace Polling for Real-Time Updates
   905→
   906→Replace AJAX polling (DataTables refresh, pipeline cache) with PostgreSQL LISTEN/NOTIFY:
   907→
   908→```sql
   909→-- On invoice finalize:
   910→NOTIFY sales_invoice_created, '{"invoice_id": 123, "branch_id": 1}';
   911→
   912→-- On challan issue:
   913→NOTIFY sales_challan_issued, '{"challan_id": 45, "warehouse_ids": [1,2]}';
   914→
   915→-- On payment:
   916→NOTIFY sales_payment_received, '{"payment_id": 78, "customer_id": 5}';
   917→```
   918→
   919→Laravel can listen via `pg_notify` PHP extension or Redis pub/sub bridge.
   920→
   921→**Why this matters for long-term**: Eliminates **polling overhead** (no more setInterval AJAX calls). Warehouse managers see new invoices **instantly** without 5-30s delay. Stock pipeline cache can be invalidated **precisely** when data changes.
   922→
   923→### 7.8 Window Functions — Replace Running Balance Denormalization
   924→
   925→Currently `customer_ledger.balance` is a denormalized running total maintained by application code. This is **fragile** — if any row is inserted out of order or modified, all subsequent balances are wrong.
   926→
   927→Replace with window-function computed balance:
   928→
   929→```sql
   930→-- Replace: SELECT balance FROM customer_ledger WHERE customer_id = ? ORDER BY id DESC LIMIT 1
   931→-- With:
   932→CREATE FUNCTION customer_current_balance(p_customer_id INT) RETURNS NUMERIC AS $$
   933→  SELECT COALESCE(SUM(debit) - SUM(credit), 0)
   934→  FROM customer_ledger
   935→  WHERE customer_id = p_customer_id AND is_reversed = false;
   936→$$ LANGUAGE SQL STABLE;
   937→
   938→-- Or for full running balance verification:
   939→SELECT id, debit, credit,
   940→  SUM(debit - credit) OVER (PARTITION BY customer_id ORDER BY id) AS computed_balance,
   941→  balance AS stored_balance
   942→FROM customer_ledger
   943→WHERE customer_id = ? AND is_reversed = false;
   944→```
   945→
   946→**Strategy**: Keep `balance` column for fast reads, but add a **reconciliation job** that verifies `stored_balance = computed_balance` using window functions. Run daily. This gives the performance of denormalization with the safety of recomputation.
   947→
   948→**Why this matters for long-term**: Running balance denormalization is the **#1 source of data drift** in accounting systems. Window functions provide a mathematically correct verification that catches any drift early.
   949→
   950→### 7.9 CTE (Common Table Expressions) — Complex Sales Queries
   951→
   952→Replace multi-query PHP patterns with single CTE queries:
   953→
   954→```sql
   955→-- Today's sales summary with payment info (currently 3+ queries)
   956→WITH today_invoices AS (
   957→  SELECT si.*,
   958→    COALESCE(SUM(ipa.allocated_amount), 0) AS paid_total,
   959→    GREATEST(0, si.total_amount - COALESCE(SUM(ipa.allocated_amount), 0)) AS balance_due
   960→  FROM sales_invoices si
   961→  LEFT JOIN invoice_payment_allocations ipa ON ipa.invoice_id = si.id
   962→  LEFT JOIN customer_payments cp ON cp.id = ipa.payment_id AND cp.is_reversed = false
   963→  WHERE si.branch_id = ? AND si.invoice_date = CURRENT_DATE
   964→    AND si.is_reversed = false
   965→  GROUP BY si.id
   966→)
   967→SELECT status,
   968→  COUNT(*) AS invoice_count,
   969→  SUM(total_amount) AS total_revenue,
   970→  SUM(paid_total) AS total_collected,
   971→  SUM(balance_due) AS total_outstanding
   972→FROM today_invoices
   973→GROUP BY status;
   974→```
   975→
   976→**Why this matters for long-term**: CTEs reduce **round-trips to DB** (1 query vs 3+), eliminate **race conditions** between sequential reads, and let PostgreSQL's optimizer choose the best execution plan for the entire operation.
   977→
   978→### 7.10 Row-Level Security (RLS) — Defense-in-Depth for Branch Isolation
   979→
   980→Currently branch isolation is enforced at middleware + model scope level. RLS provides **DB-level enforcement** that cannot be bypassed even by direct SQL:
   981→
   982→```sql
   983→ALTER TABLE sales_invoices ENABLE ROW LEVEL SECURITY;
   984→
   985→CREATE POLICY branch_isolation ON sales_invoices
   986→  USING (branch_id = current_setting('app.branch_id')::int);
   987→
   988→-- Set on each request:
   989→DB::statement("SET app.branch_id = ?", [session('branch_id')]);
   990→```
   991→
   992→**Why this matters for long-term**: If any developer forgets `BranchScope`, writes raw SQL, or a bug in middleware allows cross-branch access, RLS **still prevents data leakage** at the database level. This is the ultimate defense-in-depth.
   993→
   994→### 7.11 Table Partitioning — For Large Tables
   995→
   996→As the system grows, these tables will become very large. Range partitioning by date:
   997→
   998→```sql
   999→-- Partition sales_invoices by month
  1000→CREATE TABLE sales_invoices (
  1001→  id BIGINT GENERATED ALWAYS AS IDENTITY,
  1002→  invoice_date DATE NOT NULL,
  1003→  -- ... other columns ...
  1004→  PRIMARY KEY (id, invoice_date)
  1005→) PARTITION BY RANGE (invoice_date);
  1006→
  1007→CREATE TABLE sales_invoices_2025_01 PARTITION OF sales_invoices
  1008→  FOR VALUES FROM ('2025-01-01') TO ('2025-02-01');
  1009→CREATE TABLE sales_invoices_2025_02 PARTITION OF sales_invoices
  1010→  FOR VALUES FROM ('2025-02-01') TO ('2025-03-01');
  1011→-- ... auto-create future partitions via pg_partman ...
  1012→```
  1013→
  1014→**Candidates for partitioning:**
  1015→- `sales_invoices` (by invoice_date, monthly)
  1016→- `stock_transactions` (by transaction_date, monthly)
  1017→- `customer_ledger` (by transaction_date, quarterly)
  1018→- `journal_entry_lines` (by created_at, quarterly)
  1019→
  1020→**Why this matters for long-term**: Partitioning provides:
  1021→- **Faster queries** — PostgreSQL scans only relevant partitions
  1022→- **Faster maintenance** — VACUUM, REINDEX operate per-partition
  1023→- **Easy archiving** — Detach old partitions instead of DELETE
  1024→- **Parallel query** — Each partition can be scanned in parallel

  1026→### 7.12 EXCLUDE Constraints — Prevent Overlapping Allocations
  1027→
  1028→```sql
  1029→-- Prevent double-allocation of the same invoice amount
  1030→ALTER TABLE invoice_payment_allocations
  1031→  ADD CONSTRAINT no_overallocation
  1032→  EXCLUDE USING gist (
  1033→    invoice_id WITH =,
  1034→    numrange(0, allocated_amount, '[]') WITH &&
  1035→  );
  1036→```
  1037→
  1038→**Why this matters for long-term**: Application-level validation can be bypassed by race conditions. EXCLUDE constraints enforce **mathematical invariants** at the DB level.
  1039→
  1040→### 7.13 Deferred Constraints — For Multi-Table Atomic Operations
  1041→
  1042→Currently, some operations must INSERT rows in specific order due to FK constraints. Deferring constraints allows any order within a transaction:
  1043→
  1044→```sql
  1045→ALTER TABLE sales_invoice_items
  1046→  ALTER CONSTRAINT sales_invoice_items_invoice_id_foreign
  1047→  DEFERRABLE INITIALLY DEFERRED;
  1048→```
  1049→
  1050→**Why this matters for long-term**: Deferred constraints let PostgreSQL validate all FKs at COMMIT time rather than at each INSERT. This simplifies service code (no need to worry about insertion order) and enables batch operations.
  1051→
  1052→### 7.14 pg_cron — Replace Laravel Scheduler for DB-Level Jobs
  1053→
  1054→```sql
  1055→-- Install pg_cron extension
  1056→CREATE EXTENSION pg_cron;
  1057→
  1058→-- Schedule stale draft cleanup (runs even if Laravel queue is down)
  1059→SELECT cron.schedule(
  1060→  'cancel-stale-drafts',
  1061→  '0 2 * * *',
  1062→  $$SELECT cancel_stale_sales_drafts(14)$$
  1063→);
  1064→
  1065→-- Schedule materialized view refresh
  1066→SELECT cron.schedule(
  1067→  'refresh-ar-aging',
  1068→  '*/5 * * * *',
  1069→  $$REFRESH MATERIALIZED VIEW CONCURRENTLY mv_ar_aging$$
  1070→);
  1071→```
  1072→
  1073→**Why this matters for long-term**: pg_cron runs **inside the database** — no dependency on Laravel scheduler, queue workers, or supervisor. Even if the app server crashes, DB-level maintenance continues.
  1074→
  1075→### 7.15 Full-Text Search — Replace LIKE for Product/Customer Search
  1076→
  1077→Currently customer/product search uses `LIKE '%term%'` which cannot use indexes. PostgreSQL full-text search is vastly superior:
  1078→
  1079→```sql
  1080→-- Add tsvector columns
  1081→ALTER TABLE products ADD COLUMN search_vector tsvector
  1082→  GENERATED ALWAYS AS (
  1083→    setweight(to_tsvector('english', coalesce(product_name, '')), 'A') ||
  1084→    setweight(to_tsvector('english', coalesce(product_code, '')), 'B')
  1085→  ) STORED;
  1086→
  1087→ALTER TABLE customers ADD COLUMN search_vector tsvector
  1088→  GENERATED ALWAYS AS (
  1089→    setweight(to_tsvector('english', coalesce(customer_name, '')), 'A') ||
  1090→    setweight(to_tsvector('english', coalesce(shop_name, '')), 'B') ||
  1091→    setweight(to_tsvector('english', coalesce(mobile, '')), 'C')
  1092→  ) STORED;
  1093→
  1094→-- GIN indexes for fast search
  1095→CREATE INDEX idx_products_search ON products USING GIN (search_vector);
  1096→CREATE INDEX idx_customers_search ON customers USING GIN (search_vector);
  1097→
  1098→-- Search query
  1099→SELECT * FROM products
  1100→WHERE search_vector @@ plainto_tsquery('english', 'cement')
  1101→ORDER BY ts_rank(search_vector, plainto_tsquery('english', 'cement')) DESC
  1102→LIMIT 30;
  1103→```
  1104→
  1105→**Why this matters for long-term**: Full-text search supports:
  1106→- **Stemming** ("running" matches "run")
  1107→- **Ranking** (best matches first)
  1108→- **Multi-language** (Bengali + English)
  1109→- **Index-accelerated** (GIN index, no sequential scan)
  1110→- **Scalability** (millions of rows, sub-millisecond)

  1194→### Database Guidelines (All Phases)
  1195→
  1196→**Rule: Legacy MySQL → PostgreSQL — maximize PostgreSQL power**
  1197→
  1198→Core principles:
  1199→1. **GENERATED columns** over application-maintained denormalization
  1200→2. **Partial indexes** over full indexes for filtered queries
  1201→3. **BRIN indexes** over B-tree for append-only time-series
  1202→4. **Covering indexes** (INCLUDE) for index-only scans
  1203→5. **Window functions** for running balance verification
  1204→6. **RLS** for defense-in-depth branch isolation
  1205→7. **Advisory locks** for atomic code generation
  1206→8. **Full-text search** (tsvector + GIN) over LIKE for search
  1207→9. **Materialized views** for pre-computed reporting
  1208→10. **pg_cron** for DB-level scheduled maintenance
  1209→11. **LISTEN/NOTIFY** for real-time cache invalidation
  1210→12. **CTE** for complex multi-table queries
  1211→13. **EXCLUDE constraints** for mathematical invariants
  1212→14. **Partitioning** for large table management (future)

  1275→## Appendix B: Key Formulas Reference
  1276→
  1277→| Formula | Expression | Used In |
  1278→|---------|-----------|---------|
  1279→| Invoice total | `subtotal + transport_cost - discount_amount` | SalesInvoiceService |
  1280→| Moving average cost (IN) | `(old_qty × old_avg + in_qty × in_rate) / (old_qty + in_qty)` | StockService |
  1281→| Moving average cost (OUT) | `unchanged` | StockService |
  1282→| COGS per line | `qty × avg_cost` at challan time | SalesChallanService |
  1283→| Stock availability | `GREATEST(0, physical_qty - pipeline_qty)` | StockAvailabilityService |
  1284→| Pipeline qty | `SUM(ordered_qty - dispatched_qty)` for open invoices | StockAvailabilityService |
  1285→| Invoice balance due | `GREATEST(0, total_amount - paid_amount)` | SalesInvoiceService |
  1286→| Customer running balance | `previous_balance + debit - credit` | SubLedgerService |
  1287→| Credit limit check | `(credit_limit > 0) AND (current_due + new_amount > credit_limit + 0.01)` | SalesInvoiceService |
  1288→| GL journal balance | `SUM(debit) = SUM(credit)` within ±0.01 tolerance | JournalPostingService |
  1289→| AR reconciliation | `customer_ledger net balance = GL AR control net` | ReconciliationService |
  1290→| Inventory valuation | `SUM(warehouse_stock.qty × warehouse_stock.avg_cost)` | ReconciliationService |
  1291→| Return COGS reversal | `qty × original_cost` (not current avg_cost) | SalesReturnService |
  1292→| Transport adjustment delta | `challan_transport - invoice_transport` | SalesChallanService |
