## Surprises discovered during triage

1. **G-344 was undersold by the gap author.** The gap text framed it as "two parallel intercompany GL systems with no reconciliation" (suggesting HIGH — reconciliation break). Deeper investigation revealed that `MoneyTransferService::postIntercompanySettlement` calls `lookupLedgerByNature('intercompany')` — but NO ledger with `intercompany` nature is seeded in `basic_data_snapshot.sql` (only `interbranch_receivable` L-0105 + `interbranch_payable` L-0303 are seeded). The lookup returns null → the function silently returns null → the caller does NOT post the intercompany JE. Result: cross-branch money transfers post the cash/bank GL but SILENTLY SKIP the intercompany settlement. This is a MISSING GL POST on a financial action → CRITICAL (not HIGH as the gap author's framing suggested).

2. **G-338 was a false positive — but triage revealed an ADJACENT bug.** The gap speculated that `BranchDemandWeeklyReportService::getWarehouseWiseSales` (uses `sii.amount`) "may reference nonexistent column" because "other sales services use `sii.total`." Verification against `04_sales.sql:94` confirmed `amount` IS the correct column (`amount numeric(14,2) GENERATED ALWAYS AS (qty * rate) STORED`). However, the gap author's reference to "other sales services use `sii.total`" pointed to a REAL bug in `BranchDemandRepricingService.php:705` which uses nonexistent `sii.total` (should be `sii.amount`). This adjacent bug should be FILED AS A NEW GAP — it would crash at runtime if the repricing audit path is invoked. The triage of G-338 effectively discovered a CRITICAL bug not in the original 38.

3. **G-319 and G-340 are NOT duplicates despite identical source file:line.** The extractor picked the same surrounding table-row text for both because they appear on the same line in the dimensions file's "Who uses it?" table (Manager row): `⚠️ G1 — cannot see NULL-branch dimension values (BranchScope excludes them); G18 — can create/edit dimensions (should arguably be admin-only)`. The register's truncated summaries are byte-identical, but the underlying Orig IDs (G1 vs G18) and concerns (BranchScope bug vs route-middleware design) are distinct. The task spec suspected them as duplicates — verified DISTINCT. Both rows were updated with their respective severities (G-319 = HIGH, G-340 = MEDIUM).

4. **G-331 (reversal path inconsistency) is HIGH, not CRITICAL.** The rubric explicitly lists "reversal path inconsistency" as a CRITICAL example. However, the inconsistency here is BETWEEN modules (BranchDemand uses `JournalPostingService::reverseJournalEntry` directly + separate `reverseLedgerByReference` call; CustomerPaymentService uses `JournalReversalService::reverseByJournalEntry` for automatic cascade). The BranchDemand reversal path itself is INTERNALLY CONSISTENT — both GL JE and branch_ledger ARE reversed. The gap is a code smell / pattern divergence with future regression risk (a dev who expects the canonical cascade could forget the manual sub-ledger call). Marked HIGH with the ambiguity noted.

5. **G-335 (asset master data editable after depreciation posted) is a silent CRITICAL.** The `FixedAssetController::update` only checks `isDisposed()` — NOT whether depreciation has been posted. Editing `acquisition_cost` after depreciation schedules exist recalculates `net_book_value` but does NOT recalculate past depreciation JEs. The GL has the OLD depreciation amounts; the asset master data has the NEW cost. Silent financial misstatement. Easy to miss because the UI allows the edit without warning.

6. **G-330 (depreciation schedule uniqueness) is a CRITICAL race condition on a financial posting.** The migration creates only a non-UNIQUE INDEX on `(fixed_asset_id, period_from, period_to)` — the application-level existence check (DepreciationService.php:180-188) is the only protection. Two concurrent `generateSchedule` calls both pass the check and both insert schedules → both post depreciation JEs → DOUBLE-POSTED depreciation. Per rubric "Race conditions = CRITICAL when on a financial posting."
